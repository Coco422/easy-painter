# 充值中心

充值中心使用后端订单 + ZPAY 托管收银台，当前仅收款和加丝；不提供现金提现、佣金发放或自动现金退款接口。SDK 审查依据见 [安全审查](zpay-sdk-security-review.md)。

## 默认状态与配置

V13 预置「10 元 / 100 付费丝 / 0 赠送丝」套餐，初始停用。管理后台「充值管理」包含支付配置、套餐和订单三个区域，收款开关和套餐须分别开启。

服务器只需初始化一次私有加密主密钥：

```bash
python3 scripts/init-payment-encryption-key.py --env-file .env
```

脚本将随机生成的 Fernet 主密钥写入服务器 `.env` 的 `PAYMENT_CONFIG_ENCRYPTION_KEY`，不输出值、不覆盖已有值。API 与 worker 加载环境后即可使用后台配置；后续修改商户信息即时生效，无需重启。主密钥不保存在数据库，不复用 JWT/管理员密钥；必须随私有 `.env` 一起备份，不能直接替换或丢失，否则已有配置和旧订单无法解密。Fernet 提供认证加密，使用现有 `cryptography` 库，不自行设计密码算法，见 [Fernet 文档](https://cryptography.io/en/latest/fernet/)。

在「管理后台 → 充值管理 → ZPAY 支付配置」填写：

| 字段 | 填写内容 |
| --- | --- |
| 商户 ID（PID） | ZPAY 会员中心提供的商户 ID |
| 商户密钥（KEY） | ZPAY 商户密钥；保存后不回显，留空保留，输入新值替换 |
| 支付网关根地址 | 当前文档为 `https://zpayz.cn`；不填写会员中心地址或接口路径 |
| 网站公网地址 | 用户访问本站的规范 HTTPS 根地址，不带路径 |
| 已开通的支付方式 | 只勾选 ZPAY 已开通的支付宝/微信渠道 |
| 开放在线收款 | 配置完成后开启并保存，再上架所需套餐 |

- 会员文档来源：[ZPAY 开发文档](https://member.z-pay.cn/member/doc.html)；公开镜像：[官方文档](https://z-pay.cn/doc.html)。使用 `/submit.php` 托管收银台与 `/api.php?act=order` 查单，金额和订单由本站后端确定。商品名带「AI绘图额度」及套餐名称。
- 网关、公网地址必须是 HTTPS **根地址**，不能包含接口路径、查询参数、用户名或密码。不根据客户端 Host 自动生成回调；表单只预填当前页面来源供管理员确认。
- `notify_url` 固定为 `/api/v1/payments/zpay/notify`，`return_url` 为 `/recharge/return`。两者均不带预置查询参数。
- CDN 的 `/api/*` 不缓存和无交互挑战策略应覆盖支付通知与查单入口；不要全站关闭防护。
- V14 的 `payment_configurations` 每次保存新增不可变配置版本，商户密钥以 Fernet 密文保存，并在加密载荷中绑定版本、商户与网关。订单保存 `config_revision`，更换商户后旧订单仍读取原版本密钥；旧配置不删除。更换商户或网关须重新填写对应密钥，避免误用原密钥。
- 关闭收款只阻止新付款入口，原订单回调、补查仍继续。正式启用后由运营以自有账号小额验证支付与到账账本；本地模拟不代表真实收款验证。
- `GET/PUT /api/v1/admin/recharge/config` 仅管理员可访问，响应 `private, no-store`；只返回密钥是否已设置及加密就绪状态，不返回密钥或密文。保存使用 `expected_revision` 防止并发覆盖，冲突返回 409；缺少主密钥返回 503。公共套餐接口只展示已开放的支付方式，后端也拒绝未开放方式。
- 原 `ZPAY_*` 环境变量保留兼容；尚未通过后台保存时才作为默认配置，旧环境订单继续使用原环境凭证。`ZPAY_ORDER_TTL_MINUTES` 仍控制链接有效期。新部署无需在 `.env` 填商户密钥。

## 到账与重试

1. 登录用户选择套餐与支付方式；提交套餐 ID、版本和 `Idempotency-Key`，金额只取数据库。
2. 订单保存套餐价格/额度快照。套餐变更只作用于新订单；用户持旧套餐版本下单收到 409，必须重新确认价格。
3. 前端展示订单摘要，用户点击按钮才 POST 到 ZPAY 收银台。网络不确定时保留原请求键；历史未过期订单可继续同一笔支付。
4. 通知必须通过验签、字段去重、商户/金额/方式匹配，再经服务器向 ZPAY 主动查单确认。订单、加丝流水与两类额度批次在同一事务落库。
5. 重复通知只返回成功，不重复加丝；平台流水号与充值入账键都有唯一约束。浏览器返回页与 GET 订单接口没有直接发放额度的权限。
6. 用户与管理员可以主动核实订单。后台每分钟调度 worker 对最近 30 天待确认订单补查，每批最多 10 笔，每笔至少间隔 5 分钟；网络请求不阻塞 dispatcher 心跳。超出窗口的旧订单仍能手动核实。

支付链接默认 30 分钟有效。过期只限制继续展示收银台表单，不否认之后经平台确认的真实付款。平台服务暂不可用时保持待确认并提示不要重复付款。

## 为返佣保留的数据

- 充值订单：不可变套餐版本、实付金额（人民币分）、付费丝、赠送丝、用户 ID、商户/网关、支付方式、平台订单号与到账时间。
- 实付金额是用户支付的总额，不等于扣除平台手续费后的净结算款或利润。当前接口未确认净结算字段；若未来佣金以净结算款为基数，应通过平台流水号匹配结算对账数据，不能自行推定手续费。
- `credit_lots`：每批额度的来源与剩余数量。付费充值具有现金基数；赠送、兑换码、管理员加丝和迁移前余额的现金基数均为零，不推定其属于现金收入。
- `credit_allocations`：每笔生成预扣和管理员扣减使用哪些批次。非现金批次优先消耗，再按付费批次 FIFO；按模型/用户组实际扣丝数量分摊。
- 每条分摊保存原批次 `amount_fen_snapshot` 与 `total_credits_snapshot`。精确对应实付金额为 `amount_fen_snapshot × credits / total_credits_snapshot`；未来佣金应累计高精度金额后结算，不能每笔小额任务先取整到分。
- 失败退丝恢复原批次并标记原分摊已冲回；预扣未成功结算以及已冲回的分摊不能计算佣金。迁移前已经预扣、升级后失败的任务没有历史来源，退款归为零现金基数的旧余额。

后台对账发现额度来源总数高于账本余额会报错，避免静默改写付费来源。人工现金退款以后需要独立的退款/额度撤销/佣金冲正流程；当前不要用普通管理员扣丝冒充现金退款。

## 迁移与验证

V13 新增充值和来源表，并对现存正余额建立零现金基数的 legacy 批次，不修改用户余额、已有任务价格或历史账本；V14 新增加密配置版本与订单配置引用。依赖 V1–V12；当前 readiness 要求 V14。上线遵循正式版本与备份流程，不在本地开发过程中连接生产数据库。

升级时先备份并停写，API、worker、dispatcher 必须一起升级到同一正式版本，不能混跑旧扣丝/退丝逻辑。V13 扩展账本类型约束以接受 `recharge`；首笔充值到账后，旧版本 ORM 无法识别该类型，且旧版本 schema 检查不匹配，因此不能只换旧镜像回退。优先前向修复；必须恢复备份时按灾难恢复指南评估停写后的充值与资金对账，不能删除新账本行来绕过检查。

```bash
cd backend
uv run pytest
PYTHONPATH=. uv run --with pgserver==0.1.4 python ../scripts/check-payments-postgres.py
```

演练会在临时目录启动独立 PostgreSQL，执行迁移 SQL并验证并发订单创建、到账和退丝，不使用生产连接。它不替代正式 Flyway 容器执行记录。

本地界面预览见 `scripts/preview-payments.py`；只绑定回环地址、使用临时 SQLite 与模拟支付结果，不能拿预览身份或模拟网关用于生产。

2026-10-20 本地验证：后端 325 项、前端 60 项、部署脚本 4 项测试，应用类型检查和生产构建通过。PostgreSQL 16 执行 V1–V14，12 次并发配置保存仅接受一个版本，12 次并发下单/到账/退款保持一单一次；旧订单保留原商户凭证。浏览器验证配置保存、刷新后保留、密钥不回显及关闭收款。尚未使用真实商户密钥发起付款，真实小额收款须在管理员完成配置后验证。
